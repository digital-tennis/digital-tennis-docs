## GM-01

### 구현할 동작

**공통 Unity 환경과 테스트 코트**

처음에는 그래픽 효과 없이 코트·공·플레이어 위치를 눈으로 볼 수 있는 작은 씬을 만듭니다. 세 명이 서로 다른 Unity 버전을 사용하면 통합이 어렵기 때문에 환경부터 고정합니다.

### 선행 조건과 입력

선행 조건: 없음

D1에 결정한 Unity Editor·빌드 백엔드·목표 Windows, overview의 코트 좌표.

### 출력과 반환값

실행 가능한 빈 Windows 빌드, TestCourt 씬, 환경표.

### 동작 규칙

- ProjectSettings와 필요한 Assets·Packages를 버전 관리합니다. Library·Temp 캐시는 제외합니다.
- x=좌우,y=위,z=길이, 네트 z=0과 플레이어 0/1 방향을 일치시킵니다.
- 코트는 단식 경계와 서비스 박스를 구분하고 디버그 좌표를 표시합니다.
- Editor가 아닌 Windows 실행 파일에서 씬이 열리는지 확인합니다.

### 입력과 기대 결과 예제

```text
player0=[0,0,-9],player1=[0,0,9],net z=0
기대: 두 플레이어가 반대편에 있고 서비스 박스를 좌표로 식별 가능
```

### 예외와 경계 조건

소스는 되지만 빌드가 안 되는 환경, 서로 다른 단위 스케일, 뒤집힌 코트 축을 확인합니다.

### 권장 구현 순서

1. 빈 프로젝트를 Windows로 빌드합니다.
2. 단순 도형으로 코트를 만듭니다.
3. 버전·빌드 방법을 README에 씁니다.

### 완료 판정

- 다른 팀원이 같은 버전으로 씬을 엽니다.
- Windows에서 코트·공·두 플레이어가 보입니다.

### 제출할 결과

프로젝트, TestCourt, 환경표, 최초 Windows 실행 결과.

## GM-02

### 구현할 동작

**공 이동과 바운스 판정**

공의 움직임과 규칙 판정을 분리하면 물리 이벤트가 여러 번 호출되어도 점수를 중복 계산하지 않을 수 있습니다. 단순 중력·반사부터 구현합니다.

### 선행 조건과 입력

선행 조건: GM-01

ball position/velocity, fixed dt=1/60초, 코트·네트 충돌, lastHitter, rallyId.

### 출력과 반환값

새 공 상태와 Bounce/Out/Net 사건; 사건에는 rallyId와 고유 eventId.

### 동작 규칙

- 공의 반지름과 중력·반발 계수는 설정으로 고정합니다. 초기 중력 9.81m/s², 반발 계수 0.7을 사용합니다.
- 첫 바운스 중심점이 상대 코트 경계 안인지 판정하며 라인 위는 in입니다.
- 서비스에서는 목표 서비스 박스를, 랠리에서는 상대 단식 코트를 사용합니다.
- 하나의 실제 충돌에 동일 Bounce를 반복 생성하지 않습니다.
- 경기 결과는 이 모듈이 아니라 GM-04로 전달합니다.

### 입력과 기대 결과 예제

```text
호스트가 마지막 타격, 상대편 첫바운스=[4.115,0,5]→in
첫바운스 x=4.116→out
상대 코트 안 첫바운스 후 두 번째 Bounce→호스트 득점 사건 후보
```

### 예외와 경계 조건

공이 네트를 통과하는 터널링, 동일 프레임 여러 충돌, 바깥 바닥과 네트 접촉 순서, 공이 멈춘 상태를 확인합니다.

### 권장 구현 순서

1. 한 공의 낙하·반사를 관찰합니다.
2. 경계 판정을 순수 함수로 만듭니다.
3. rallyId·이벤트 중복 방지 후 점수 모듈에 사건을 전달합니다.

### 완료 판정

- in/out·라인·첫/두 번째 바운스 사례가 맞습니다.
- 동일 충돌이 두 번 점수를 올리지 않습니다.
- 온라인에서는 호스트에서만 물리와 규칙 사건을 확정합니다.

### 제출할 결과

물리 설정, 바운스·경계 함수, 숫자 예제와 씬.

## GM-03

### 구현할 동작

**서브와 랠리 상태기계**

타격 입력이 언제 유효한지는 경기 상태가 결정합니다. 서브 대기·첫 폴트·렛·랠리·득점을 명시하면 아무 때나 스윙해 공을 치는 문제를 막을 수 있습니다.

### 선행 조건과 입력

선행 조건: GM-02, BL-01

MatchPhase, serverId, serveSide, faultCount, RacketInput, 서비스 바운스·네트 사건.

### 출력과 반환값

WAIT_SERVE/IN_FLIGHT/RALLY/POINT_END/MATCH_END와 공 초기 위치, 허용된 타격.

### 동작 규칙

- WAIT_SERVE에서는 서버의 serve 입력만 받고 리시버 입력은 무시합니다.
- 서비스는 대각 서비스 박스: player0 오른쪽(x>0)에서 player1 왼쪽(x≤0,z0~6.40), 반대는 대칭입니다.
- 유효 서비스에서 네트를 건드리면 렛으로 WAIT_SERVE 복귀하며 faultCount는 유지합니다.
- 첫 폴트는 faultCount1·재시도, 둘째 폴트는 상대 포인트·faultCount0입니다.
- 게임 내 누적 포인트 짝홀로 서비스 박스를 정합니다. 게임마다 서버를 교대하며 타이브레이크는 1포인트 뒤 2포인트씩 교대합니다. 세트·승리·엔드 교대는 TennisMatchScore가 결정합니다.

### 입력과 기대 결과 예제

```text
WAIT_SERVE host→serve→박스밖→faultCount1 WAIT_SERVE
다시 serve→박스밖→게스트 1포인트, POINT_END
serve→네트 touch+유효박스→LET, 점수와 faultCount 변화없음
```

### 예외와 경계 조건

서브 전 게스트 스윙, 서비스 중 중복 입력, 렛과 아웃 동시 사건, 결과 화면의 입력을 검사합니다. 아웃이면 폴트이며 렛으로 처리하지 않습니다.

### 권장 구현 순서

1. 상태 전이표를 숫자 입력으로 검증합니다.
2. 가상 serve와 서비스 박스 판정을 붙입니다.
3. 점수와 공 재배치·다음 포인트를 연결합니다.

### 완료 판정

- 두 폴트·렛·유효 서비스가 예제대로 동작합니다.
- 허용되지 않은 상태 입력은 공을 바꾸지 않습니다.

### 제출할 결과

상태기계, 서비스 박스 표, 서브·렛·폴트 시연.

## GM-04

현재 구현에서는 아래 포인트 함수의 WIN은 **한 게임 획득**입니다. `TennisMatchScore`가 이를 받아 게임→세트→경기 승리와 서버/엔드 교대를 계산합니다. 기본 3세트 중 2세트 선승, 세트 6게임·2게임 차, 6–6 타이브레이크 7점·2점 차를 사용합니다. 결과 화면은 한 게임 종료가 아니라 경기 승리에서만 열립니다. 예를 들어 5–5에서 한 게임을 이기면 6–5로 계속하고, 6–6 타이브레이크 7–6도 계속하며 8–6이면 세트가 종료됩니다. 규칙은 rules.csv에서 읽고 다음 경기부터 적용합니다.

### 구현할 동작

**순수 점수 함수와 중복 득점 방지**

점수 계산은 Unity 씬 없이 테스트할 수 있게 만듭니다. 물리 콜백이 겹쳐도 한 rallyId에서 한 포인트만 반영합니다.

### 선행 조건과 입력

선행 조건: 없음; GM-03에 이후 통합

누적 points[2], pointWinner, rallyId, 이미 종료된 rallyId 집합.

### 출력과 반환값

새 points, 표시 점수, deuce/advantage/winner, 다음 서비스 사이드.

### 동작 규칙

- 0/1/2/3포인트는 0/15/30/40으로 표시합니다.
- 양쪽 3이상에서 같으면 deuce, 차이 1이면 advantage, 한쪽 4이상이고차이 2이상이면승리입니다.
- 승리 이후 point 사건을 무시합니다.
- 같은 rallyId의 득점은 한번만 처리하며 첫 판정 결과를 유지합니다.

### 입력과 기대 결과 예제

```text
[3,3]→host 득점→[4,3],ADV host
→guest 득점→[4,4],DEUCE
→host2회→[6,4],WIN host
같은 rallyId의중복 point→점수변화없음
```

### 예외와 경계 조건

음수 포인트, 없는 플레이어, 서로 다른 winner의 중복 사건, 승리 후 사건, 긴 듀스를 검사합니다.

### 권장 구현 순서

1. 표시 점수 순수 함수를 만듭니다.
2. 승리 조건을 독립 검증합니다.
3. rallyId 처리와 다음 서비스 사이드를 연결합니다.

### 완료 판정

- AT-09와 일반 0→40→승리 사례가 맞습니다.
- 중복 충돌·중복 네트워크 결과가 추가 포인트를 만들지 않습니다.

### 제출할 결과

순수 점수 모듈, 예제 출력, 중복 사건 테스트.

## GM-05

### 구현할 동작

**라켓 입력으로 샷과 자동 이동**

게임은 RacketInput을 받아 타격 구간에서 샷을 결정합니다. BLE와 키보드는 같은 경계를 사용하며 캐릭터 이동은 자동화합니다.

### 선행 조건과 입력

선행 조건: GM-02/03/04, BL-01/03

RacketInput, 플레이어 위치, 공 위치·phase, 예상 도달 위치.

### 출력과 반환값

허용된 타격의 velocity와 마지막 타격자, 자동 이동 목표와 위치.

### 동작 규칙

- 초기 타격 거리 한계 1.5m, 공 높이 0.2~2.5m, 같은 incoming-ball 구간에서는 1회 타격입니다.
- 이동 속도 초기 5m/s, 목표는 자신의 코트 안 예상 타격 위치로 clamp 합니다.
- 샷 속도 초기 10+12*power01 m/s, 좌우각 aimX*25 도, 상향각 20+10*aimZ 도로 설정합니다.
- player0 전방은+z,player1 전방은-z이므로 코트 변환을 한 번 적용합니다.
- 게임 입력이 너무 늦거나 phase가 끝났으면 타격하지 않고 miss를 기록합니다.

### 입력과 기대 결과 예제

```text
power01=0.5→샷 속도 16m/s
aimX=0,aimZ=0,player0→좌우중립,+z·상향 20 도
같은 eventId 반복→타격 1회
공과거리 3m→miss
```

### 예외와 경계 조건

범위 밖/NaN 입력, 너무 늦은 스윙, 좌우 플레이어 방향 반전, 이동 목표 코트 밖, 공 없는 상태를 검사합니다.

### 권장 구현 순서

1. 가상 입력을 공속도로 바꿉니다.
2. 타격 구간과 중복 방지를 추가합니다.
3. 자동 이동과 실제 BLE source를 연결합니다.

### 완료 판정

- 가상/실제 source 변경이 점수·샷 코드 변경을 요구하지 않습니다.
- 타격 가능한 스윙만 공을 바꿉니다.
- 서로 반대편 플레이어가 자기 전방으로 공을 칩니다.

### 제출할 결과

샷 매핑 설정, 이동 함수, 가상·실물 입력 시연.

## GM-06

### 구현할 동작

**1인 모드와 메뉴·상태 UI**

플레이어는 연결 상태와 보정 필요 여부를 보고 AI 난이도를 선택해야 합니다. AI는 이동·타격 의사결정을 표준 게임 입력으로 전달합니다.

### 선행 조건과 입력

선행 조건: GM-05, AI-01/03, BL-04

AI difficulty, ControllerSource 상태, game phase, 온라인 여부.

### 출력과 반환값

메뉴·난이도 선택·연결·보정·점수·일시정지·결과 화면, 1인 경기.

### 동작 규칙

- single-player에서 상대에만 AI를 활성화합니다.
- online에서 양쪽 AI는 비활성화하고 원격 입력을 받습니다.
- BLE 끊김·보정 실패·서버 연결 실패는 원인과 다시 시도 동작을 보여줍니다.
- 한 개 스윙이 메뉴 확인과 공 타격을 동시에 수행하지 않도록 현재 화면이 입력을 소비합니다.
- 테스트 환경·연결 모드는 디버그 화면에서 확인할 수 있게 합니다.

### 입력과 기대 결과 예제

```text
single-player/easy 선택→player1 easy 정책
online 참가→AI 비활성
BLE 단절→경기일시정지·재연결 안내
MATCH_END→승자·다시시작
```

### 예외와 경계 조건

게임 중 난이도 변경은 다음 경기부터 적용합니다. 연결되지 않은 장치, 가상 source, 중복 start 버튼, 결과화면 타격을 검사합니다.

### 권장 구현 순서

1. 가상 input으로 메뉴→경기를 연결합니다.
2. AI adapter와 난이도를 붙입니다.
3. 연결/실패/결과 화면을 검증합니다.

### 완료 판정

- AI 세 난이도로 1게임씩 진행할 수 있습니다.
- 연결과 게임 상태가 화면에서 구별됩니다.
- online에서 AI가 원격 플레이어를 조종하지 않습니다.

### 제출할 결과

UI 씬, AI adapter, 모드별 시연과 상태표.

## GM-07

### 구현할 동작

**온라인 로비와 P2P·릴레이 전송 어댑터**

MatchClient는 game 저장소에 있고 서버는 방과 연결 정보만 관리합니다. 코드로 두 PC를 연결한 뒤 같은 게임 메시지를 P2P 또는 릴레이로 보낼 수 있어야 합니다.

### 선행 조건과 입력

선행 조건: MS-02/03/04, 온라인 계약; A/C 공동 검토

서버 URL, create/join 코드, 온라인 계약, D3 검증된 P2P 후보.

### 출력과 반환값

방 로비와 peer 상태, IGameTransport 구현, 양쪽 같은 mode·epoch.

### 동작 규칙

- D3까지 최소 Windows 빌드 2개가 작은 문자열을 DataChannel로 교환하는 spike를 먼저 제출합니다.
- create/join과 offer/answer/ICE를 서버로 보내며 socket의 방 membership을 사용합니다.
- P2P8초 실패 후 host propose→guest ack→host commit→서버 committed를 양쪽에서 확인합니다.
- 전송 mode가 확정되기 전 게임 입력을 보내지 않습니다. P2P에서도 WebSocket 제어 연결은 유지합니다.
- 한 mode 변경마다 epoch를 증가시키고 이전 epoch 메시지를 버립니다.

### 입력과 기대 결과 예제

```text
코드 AB2CD3에두 PC 참가→room.ready→signal
DataChannel 준비→mode=p2p,epoch1 합의
강제실패→8초후 mode=relay,epoch1 합의
모드전환→pause,epoch2,checkpoint 후 resume
```

### 예외와 경계 조건

없는 방, 만원, 호스트/게스트 역할 혼동, 후보 미호환, 오래된 ICE, 한쪽만 전환, P2P 끊김을 확인합니다.

### 권장 구현 순서

1. D3 spike에서 후보·버전을 고정합니다.
2. 릴레이로 코드 참가와 메시지 전달을 완성합니다.
3. P2P를 같은 경계에 붙이고 직접·중계 경로를 분리 검증합니다.

### 완료 판정

- AT-12/13/14를 각각 판정합니다.
- 직접 경로 후보와 서버 중계 카운터로 구분할 수 있습니다.
- 한쪽만 mode를 변경하여 서로 다른 경기를 진행하지 않습니다.

### 제출할 결과

MatchClient, P2P/relay adapter, spike 환경·직접경로·실패 전환 로그.

## GM-08

### 구현할 동작

**호스트 권위와 상태 동기화·재접속**

Unity 물리를 두 PC에서 동시에 권위 있게 계산하면 공과 점수가 달라집니다. 호스트 한쪽이 결과를 확정하고 게스트는 최신 상태를 보여줍니다.

### 선행 조건과 입력

선행 조건: GM-04/07, MS-05

input/snapshot/result/pause, epoch, inputSeq, tick, 호스트 물리 상태.

### 출력과 반환값

두 PC의 같은 points/phase/result, 부드러운 게스트 표시, 재개 시 같은 checkpoint.

### 동작 규칙

- host 만 60Hz 물리·점수, 30Hz snapshot을 만듭니다.
- guest는 입력을 보내고 호스트 snapshot을 100ms 지연 버퍼로 보간합니다. 초기 MVP에서 guest 물리는 표시용 공을 확정하지 않습니다.
- 입력의 중복·role·범위·타격 구간을 검사하며 guest가 보낸 snapshot·result는 거절합니다.
- snapshot은 tick·epoch가 새 값일 때만 적용합니다. 순번 wrap은 계약 규칙을 사용합니다.
- 끊기면 pause 합니다. 유예 15초 내 resume 시 마지막 host snapshot과 새 epoch를 확인한 뒤 재개합니다. 호스트 복귀 실패는 무효 종료합니다.

### 입력과 기대 결과 예제

```text
inputSeq42가 2회수신→호스트타격 1회
snapshot tick120 후 tick119→119 무시
guest가 points[99,0]발행→거절
유예내복귀→같은 points·rallyId로재개
```

### 예외와 경계 조건

지연 100ms, 역순/중복 패킷, 모드 전환, pause 중 입력, snapshot 누락, 유예 이후 resume를 확인합니다.

### 권장 구현 순서

1. 릴레이에서 호스트 snapshot을 표시합니다.
2. 중복·역순·역할 검사를 넣습니다.
3. P2P에서도 같은 메시지를 검증하고 pause·resume를 붙입니다.

### 완료 판정

- 양쪽의 득점·승자가 동일합니다.
- AT-15~17에서 중복 득점·tick 역행·끊김 후 진행이 없습니다.
- 모든 peer가 새 epoch를 확인하기 전에는 재개하지 않습니다.

### 제출할 결과

동기화·보간·checkpoint 처리, 지연 주입 도구, 양쪽 로그.

## GM-09

### 구현할 동작

**Windows 릴리스와 재현 가능한 플레이 검증**

팀원의 Editor에서 실행되는 것만으로 PC 제품 완료를 판단하지 않습니다. 다른 Windows PC에서 실행 파일·컨트롤러·서버 설정을 재현해야 합니다.

### 선행 조건과 입력

선행 조건: GM-06/08, AI-04

최종 제품 SHA와 버전, Windows 빌드, 서버 endpoint, 실물/가상 source.

### 출력과 반환값

실행 파일 릴리스 후보, 설치·실행 안내, 수용 테스트 기록, 알려진 문제.

### 동작 규칙

- 빌드 백엔드·Unity·OS·BLE 패키지·P2P 후보 버전을 기록합니다.
- 하드웨어·서버 없이 가능한 가상·1인 데모와 온라인 준비 절차를 구분합니다.
- 실행 파일은 릴리스 자산으로 제공하고 큰 캐시·민감한 설정은 소스에 넣지 않습니다.
- P2P 미완료나 실물 한 세트의 제한은 실제 상태대로 표시합니다.

### 입력과 기대 결과 예제

```text
새 PC→안내대로실행→virtual source/easy→1게임
BLE 준비→보정→실물타격
두 PC→코드→직접 P2P·강제 relay를각각확인
```

### 예외와 경계 조건

실행 의존성 누락, 잘못된 endpoint, BLE/P2P 오류, 무한 로딩, 결과 후 재시작을 검사합니다.

### 권장 구현 순서

1. 릴리스 후보를 빌드합니다.
2. 다른 팀원이 안내대로 실행합니다.
3. 결함 수정 후 관련 검증만 반복하고 최종 SHA를 고정합니다.

### 완료 판정

- AT-18과 필수 게임·온라인 검증에 실제 결과가 있습니다.
- 설치 안내만으로 시연을 재현할 수 있습니다.

### 제출할 결과

Windows 빌드, README, 영상·로그·수용 테스트 표.
