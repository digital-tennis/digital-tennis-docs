GitBook 목차, 제품별 과제, 일정, 수용 테스트, 포트폴리오 증거를 구현합니다. 아래 과제는 아직 구현하지 않은 문제 명세입니다. 각 입력·출력과 예제를 먼저 재현하고 예외 조건을 추가하세요. [WBS](../planning/wbs.md)의 과제 번호로 작업을 연결합니다. 초기 숫자 설정은 실제 환경 검증 후 변경 이력과 함께 조정할 수 있습니다.

## DC-01

### 구현할 동작

**제품 과제와 환경표를 한 곳에 정리**

경험이 적은 팀원이 각 저장소의 책임과 첫 번째 작업을 알아야 합니다. 과제는 기능 목록뿐 아니라 입력·출력·예제·오류·완료 조건을 제공합니다.

### 선행 조건과 입력

선행 조건: 없음

7개 저장소, 외장 IMU 조건, 12일·3인 범위, 제품별 과제와 D1 환경 결정.

### 출력과 반환값

docs/products/의 7개 과제 문서, 저장소 표, 실제 환경표와 결정 기록.

### 동작 규칙

- IMU가 내장되어 있다고 설명하지 않습니다.
- firmware 드라이버와 motion 인식, WebSocket 시그널링과 직접 P2P 책임을 구분합니다.
- 미확정 핀·모델·버전은 실제 선택 후 기록합니다.
- 각 과제는 다른 제품의 완성을 기다리지 않는 모의 검증 입력을 설명합니다.

### 입력과 기대 결과 예제

```text
학생이 PR-02를열음→20 바이트입력·반환값·BAD_CRC 예제확인
FW-01을열음→아직모델미정이면확정부터시작
```

### 예외와 경계 조건

잘못된 저장소 링크, 미구현 기능의 완료 표시, 문서 없는 오류 코드, 근거 없는 핀맵을 확인합니다.

### 권장 구현 순서

1. 제품별 문서를 한 개씩 읽고 과제 ID를 대조합니다.
2. D1 환경표를 실제로 채웁니다.
3. 학생이 한 문제를 읽고 구현해야 할 동작을 설명해 보게 합니다.

### 완료 판정

- 모든 제품에 상세 과제가 있습니다.
- 초급자가 예제와 완료 기준을 독립적으로 찾습니다.

### 제출할 결과

환경표·7개 과제·결정 기록·개선 사항.

## DC-02

### 구현할 동작

**GitBook 목차와 연결 검증**

문서는 GitHub에서도 읽히고 GitBook Free의 한 Space로 가져올 수 있어야 합니다. 팀 협업은 GitHub PR로 진행하며 GitBook 편집자 수와 혼동하지 않습니다.

### 선행 조건과 입력

선행 조건: DC-01

.gitbook.yaml, docs/README.md, docs/SUMMARY.md, 문서·이미지 상대 링크.

### 출력과 반환값

목차·설정·링크 검증 결과. 실제 연결 시 GitBook 사이트 주소.

### 동작 규칙

- 한 Markdown 파일은 SUMMARY에 한 번만 등장합니다.
- 이미지는 docs/assets에 보관하여 문서 root 안에서 읽을 수 있게 합니다.
- 최초 sync는 GitHub → GitBook을 선택합니다.
- 실제 GitBook 계정 연결·앱 승인은 계정 소유자가 수행하며 저장소 준비와 연결 완료를 구별합니다.

### 입력과 기대 결과 예제

```text
SUMMARY의 products/digital-tennis-ai.md→실제파일존재
GitBook에서 AI과제열기→입력/출력/예제와이미지정상
GitHub 문장변경후 merge→GitBook 반영
```

### 예외와 경계 조건

없는 파일·중복 페이지·root이중 적용·한글 링크·앱 저장소 접근 누락을 검사합니다.

### 권장 구현 순서

1. 로컬 상대 링크와 목차 중복을 검사합니다.
2. 설정의 root를 확인합니다.
3. 실제 계정 연결 후 작은 수정으로 양방향 동작을 확인합니다.

### 완료 판정

- 로컬 목차·이미지·링크가 정상입니다.
- 실제 계정 연결을 했다면 AT-19 증거가 있습니다.

### 제출할 결과

GitBook 설정·목차·연결 가이드·검증 결과.

## DC-03

### 구현할 동작

**수용 테스트 결과와 통합 증거**

계획과 완료 결과를 구분하려면 테스트 ID 별 환경·실제값·판정이 필요합니다. 개발 후 증거를 모으고 실패를 감추지 않습니다.

### 선행 조건과 입력

선행 조건: 제품구현·testing/acceptance.md

AT-01~19 계획, 제품 SHA, 로그·영상·사진, 실물 수량·네트워크 환경.

### 출력과 반환값

Pass/Fail/Blocked 결과표, 재현 가능한 Issue, 관련 증거 링크.

### 동작 규칙

- 각 결과는 기대값과 실제 관측을 분리합니다.
- 실물과 가상 입력, 직접 P2P와 릴레이, Editor와 Windows 빌드를 구분합니다.
- 실패에서 재현 조건·담당자·다음 행동을 기록합니다.
- 공개 증거에는 token·개인 키·불필요한 민감정보를 제거합니다.

### 입력과 기대 결과 예제

```text
AT-13:P2P 실패→Fail+후보/환경/원인
AT-14:relay 성공→Pass+mode/카운터
전체온라인보고:P2P 미완료,relay 완료
```

### 예외와 경계 조건

영상만 있고 버전 없음, 모의 테스트를 실기로 표기, 로그 없는 완료 체크, 다른 커밋 결과 혼용을 확인합니다.

### 권장 구현 순서

1. 같은 제품 조합 SHA를 기록합니다.
2. 각 담당자가 결과를 제출합니다.
3. 다른 팀원이 재현하고 최종 상태를 검토합니다.

### 완료 판정

- 모든 필수 경로에 실제 판정과 증거가 있습니다.
- 남은 문제가 Issue 또는 체크리스트에 있습니다.

### 제출할 결과

수용 테스트 결과표·증거 목록·남은 문제.

## DC-04

### 구현할 동작

**WBS 공수와 포트폴리오 릴리스**

12일·3명 일정을 초과하지 않고 결과물을 독립적인 포트폴리오로 정리합니다. 계획된 작업과 실제 완료를 비교할 수 있어야 합니다.

### 선행 조건과 입력

선행 조건: DC-03,PR-04

72개 반일 작업, 담당별 진행 상태, 함께 검증한 제품 SHA, README·실행 자산·영상.

### 출력과 반환값

36인일 합계·담당별 12인일 확인, 최종 버전표·릴리스·남은 작업.

### 동작 규칙

- 반일 작업 하나는 0.5인일, 각 담당·각 날짜에 2개 이하입니다.
- D11~12는 QA·수정·문서·릴리스에 배정합니다.
- 완료는 과제의 증거를 확인한 뒤 표시합니다.
- 라이선스·제 3 자 자산 사용 조건은 팀이 확인 후 선택합니다.

### 입력과 기대 결과 예제

```text
72*0.5=36PD;A/B/C 각 24*0.5=12PD
P2P 증거없음→WBS 관련작업 Done 표시안함
제품별 README→실행법·테스트·설계·관련저장소링크
```

### 예외와 경계 조건

한 사람 하루 1.5인일, 선행 작업 미완료인데 통합 Done, 버전 없는 바이너리, README의 낡은 상태를 확인합니다.

### 권장 구현 순서

1. 공수·선행 작업을 합산합니다.
2. 실행 자산과 버전표를 고정합니다.
3. 결과와 남은 작업을 포트폴리오에 연결합니다.

### 완료 판정

- 일정이 12일·3명·36인일 범위입니다.
- 각 제품을 문서와 결과로 독립적으로 설명할 수 있습니다.

### 제출할 결과

최종 WBS·SHA 표·제품 README·시연·남은 문제.
