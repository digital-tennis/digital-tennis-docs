# 초보 개발자의 작업과 제출 방법

과제 하나의 예제를 읽고 작은 동작을 먼저 구현한 뒤 예외 조건을 추가합니다. 혼자 전체 제품을 완성할 필요가 없습니다. WBS의 과제 번호를 작업 단위로 사용합니다.

## 역할 배정

초기 배정은 A를 경험자, B를 초급 개발자, C를 학생으로 가정합니다. A는 외장 IMU·펌웨어와 기술 검토를 맡습니다. B는 가상 입력으로 Unity 씬·점수부터 시작한 뒤 AI를 구현합니다. C는 문서·프로토콜 예제·가상 SDK·방 관리부터 시작합니다. Windows 네이티브 BLE와 P2P 후보 검증은 A와 C가 함께 검토합니다. 실제 숙련도에 따라 D1에 이름과 역할을 바꿀 수 있습니다.

## 시작 절차

1. 자신의 제품 README와 해당 상세 과제를 읽습니다.
2. 과제 번호, 예상 입력·출력, 막힌 조건을 개인 체크리스트에 적습니다.
3. 실제 구현 때 Issue를 만들고 `feat/PR-02-codec`처럼 과제 번호가 있는 브랜치를 만듭니다.
4. 정상 예제 하나를 재현한 뒤 잘못된 입력 하나를 처리합니다.
5. 실행 방법과 결과를 기록하고 커밋합니다.
6. PR에 문제·동작·검증·남은 문제를 쓰고 A 또는 동료가 확인합니다.

```sh
git clone https://github.com/digital-tennis/digital-tennis-protocol.git
cd digital-tennis-protocol
git switch -c feat/PR-02-codec
# 코드를 구현하고 과제의 예제와 실패 조건을 확인합니다.
git add <변경한-파일>
git commit -m "feat(protocol): implement PR-02 packet codec"
git push -u origin feat/PR-02-codec
```

`<변경한-파일>`은 실제 파일 경로로 바꿉니다. 위 명령은 제품 실행 명령이 아닙니다. 빌드 도구와 테스트 명령은 D1 선택 후 각 README에 추가합니다.

## PR에 제출할 내용

```text
과제: PR-02
문제: 20바이트 패킷을 공통 필드로 읽어야 함
구현: 길이·버전·CRC 검증과 little-endian 파싱
검증: 정상 스윙, 잘못된 CRC, 짧은 패킷 → 기대 결과 기록
남은 문제: 없음 / 실제로 남은 항목
```

실제 하드웨어가 필요한 문제는 배선 사진·부품 모델·펌웨어 커밋·로그를 포함합니다. 아직 실기가 없으면 모의 입력 결과로 표시합니다. 보정 실패를 성공처럼 처리하거나 오류를 숨기지 않습니다.

## 매일 협업

시작 10분: 어제 결과, 오늘 과제, 막힌 의존성을 공유합니다. 중간: A가 B/C의 위험한 통합 부분을 짧게 검토합니다. 마감 20분: 공통 버전으로 통합하고 문제를 다음 날 WBS에 반영합니다. 멘토링은 별도 4번째 인력 공수로 계산하지 않고 각자의 하루 공수에 포함합니다.

새 기능을 추가하기 전에 12일 필수 범위인지 확인합니다. 공개 저장소에는 비밀번호·토큰·개인 키·민감한 장비 주소를 올리지 않고 설정 예제만 제공합니다. 라이선스는 팀이 사용 코드·이미지의 조건을 확인한 뒤 선택하며 이 초기 문서에서 임의로 부여하지 않습니다.
